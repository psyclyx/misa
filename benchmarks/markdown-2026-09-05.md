# Markdown suffix-search regression, 2026-09-05

The public `misa.markdown.parse` path rescanned the remaining suffix twice at
almost every ordinary character. The backtick and link-label productions only
accept a match at the current cursor, so both searches now anchor there. The
source text, source ranges, parsing limits, and semantic AST are unchanged.

Baseline exploratory plain-text parses: 8 KiB 0.385 s, 16 KiB 1.499 s,
32 KiB 6.208 s. Doubling input approximately quadrupled CPU time.
`luajit -jp=l` attributed all sampled time to the two searches: 66% to backticks,
34% to link labels. This identified suffix scanning as the dominant term.

Measurements use the dev shell's LuaJIT 2.1.1785763465 with its default JIT mode,
matching native `luaL_openlibs`; Misa hides access to `jit` but does not disable
its engine. These are parser CPU times (`os.clock`), not whole-frame latency.
Builds and other agent tests were stopped during the measurement window. Samples
run sequentially with alternating baseline/candidate order, 10 samples per
variant and workload. No CPU affinity or system-wide cache manipulation was used.

| Workload              | Baseline median / best | Candidate median / best |
| --------------------- | ---------------------- | ----------------------- |
| Plain 16 KiB          | 1.497583 / 1.483128 s  | 0.006111 / 0.006033 s   |
| Mixed Markdown 16 KiB | 0.007429 / 0.007384 s  | 0.005204 / 0.005147 s   |

The measured plain paragraph improvement is about 245×. The mixed workload also
improves; neither result is near the 2% noise floor. A separate candidate-only
262144-byte plain paragraph took 0.105784 s. There is no baseline timing at that
size; the original 300000-byte selection fixture had already stalled beyond
40 s, so the paired comparison uses the smaller representative workload.

Before comparing timings, six unchanged parses per workload produced one
distinct serialized AST. Every timed result was compared byte-for-byte to that
oracle. A separate seeded corpus of 1009 Markdown/fuzz inputs also produced
byte-identical ASTs. `tests/markdown.fnl` exercises the original 300000-byte
input, truncation, source ranges, and inline syntax following plain prefixes.
Its integration invocation has a generous five-second timeout to catch the
original runaway scan without requiring benchmark-grade CI timing stability.

Raw samples: `markdown-2026-09-05.csv`.

Reproduction:

```sh
tools/fennel benchmarks/markdown.fnl /path/to/baseline.lua extensions/markdown.fnl 16384 10
tools/fennel benchmarks/markdown-parity.fnl /path/to/baseline.lua extensions/markdown.fnl
```

The baseline is the same parser with the two cursor anchors removed:
`text:find("(`+)",at)`plus its existing`tick_first~=at`check, and`text:find("%[([^%]]-)%]",at)`plus its existing`label_start~=at`check.

the candidate SHA256 was
`743dbffc343301e9e4f63444fc790664d5ce5587fd0eba3e01b5fb1a35e07e72`.

No discarded optimization variants. This change removes the measured ordinary
paragraph pathology; it is not a claim that every adversarial Markdown input
has linear worst-case complexity.
