# Parity with the previous TUI

The old misa shipped one terminal frontend with a great deal in it. This records what of
that has a home in the new architecture, whether it is built, and — where it is not — which
mechanism it is waiting on.

Parity here does not mean the same pixels. It means the same **capability**, expressed in
each platform's own idiom: a collapsible is a `<details>` in a browser and a rail plus
indentation in a terminal, and both are correct. What must not differ is what a person can
_do_.

`cargo test --workspace` is the gate: 471 tests, thirteen more behind
`misa-plugin --features guest-fixture`, and one behind `misa-skia --features paint` — a feature
`plan.md` phase 7 deletes, at which point that test joins the gate. Counts per crate are in
`docs/architecture.md`.

## Blobs, end to end

A blob is named by the hash of its content, and that one decision is what makes the rest of
this simple: a name cannot be a path, so a client cannot ask for `/etc/shadow` by calling it
one; it cannot be handed different bytes than it asked for; and the bytes behind a name can
never change, so the browser may cache them forever and a transcript that scrolls back
fetches nothing.

Three things move the bytes, and they are deliberately three:

- **The store** (`misa-kernel::blobs`) holds them, in memory or on disk, sniffs what they
  are, bounds how large they may be, and has no notion of who is asking.
- **The connection** (`misa-net::blob`) serves and fetches them over `/misa/blob/0`, with the
  roster checked before a message is read. It is a separate connection from the session on
  purpose: a 4 MiB image queued in front of a token stream would be worse than a second
  connection, and raising `MAX_CONTROL_FRAME` for every message so that images could travel
  would remove the bound that keeps a hostile peer from making a client allocate.
- **The client** (each frontend) decides what to fetch and what to send. The web frontend
  serves `/blob/<hash>` to the browser and takes a file input; the terminal cannot draw one,
  so its renderer shows the alt text carried by the same image node every client receives.

What is still missing is a _client-side_ copy of a blob that a person could keep: a file
input uploads and a view shows, and nothing writes a received image to a directory.

## What moved, on purpose

- **A report is a panel the session opens and a client draws.** `/status` and `/usage` are
  session commands because the facts are the session's, and a panel is presentation _policy_
  — what a report contains — which lives in the middle layer once. The layout is not: a
  `<dl>`, a table, and two wrapped lines are three right answers. Help stays a client action,
  because the declarations are already in hand.
- **Copy is client-side.** The previous system emitted a `clipboard/write` effect, which
  meant a session could write to a clipboard. Only the client knows what was selected.
- **The picker is client-side and the candidates are not.** What is choosable is declared;
  what is filtered is local.
- **A credential is a slot.** Policy names it; the daemon injects it. That is the previous
  system's rule, and it is what makes an effect boundary a security boundary rather than a
  convention.
- **The clipboard, the terminal, the filesystem, and the network are capabilities**, so
  they are kernel requests rather than effects a policy can invent.

## Where the frontends differ, and why that is right

|             | terminal                                                                 | browser                                                                                     | pixels                                              |
| ----------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Picker      | `misa-client::picker`, drawn as lines                                    | a `<datalist>` from the declarations, no script                                             | not built: the scene draws, it does not choose      |
| Collapsible | a summary line, body indented                                            | `<details>`                                                                                 | a summary and a body; no toggle yet                 |
| Theming     | a role to ANSI style                                                     | a role to a CSS custom property                                                             | a role to a paint                                   |
| Input       | modes and motions                                                        | a `<textarea>`                                                                              | not built; a window and input are `plan.md` phase 8 |
| Transport   | iroh                                                                     | HTTP to its own server, which speaks iroh                                                   | iroh                                                |
| Selection   | `misa-client::select`, copied by OSC 52                                  | the browser's own text selection, no script                                                 | not built                                           |
| Panel       | modal while it is up: a field takes the keys, Enter sends, Esc dismisses | a `<form>` for the fields and one small form per action, so its buttons work with no script | the node and its actions; no interaction yet        |
| Diff        | a role per line: added, removed, hunk                                    | the node's role as a class; its lines are a block                                           | the node's role as a paint; lines are a block       |

The crate names above are today's. `plan.md` phase 4 renames the kit to `misa-kit` and splits
`misa-net` into `misa-protocol` (both ends of the protocol state machine) and `misa-transport`
(bytes), so every row that says `misa-client::…` becomes `misa-kit::…`.

`android/` is a fourth surface and not one of these three: a Kotlin app over the same Rust
client, whose own `README.md` records what it draws today — the transcript, the palette, the
composer — and that an image is words until it can fetch a blob.

The web frontend is the proof that the boundary is real: it uses _none_ of the picker kit and
still offers the same commands, because what it needed was the declaration.

## What is left, and in what order

This file says what is _built_; [`plan.md`](plan.md) says what is next and in what order, including
the two items this section used to list — a client that keeps what it receives (with cancelling a
device flow a client started, which is the same shape of work), and the pixel frontend's window
alongside the same memory for the browser and the phone.

Saving attachments: the terminal offers `/save [number] <local path>` and the browser offers Save attachment. Both request the session-advertised `attachment.save`, receive a directed kernel metadata answer, and fetch the bytes over the blob protocol. Terminal writes create a new file and refuse overwrite; browser responses are downloads. Android and pixel destination selection remains frontend work.
